# PAD_HW

Учебный проект курса ПАД: репозиторий, в который нельзя влить код с ошибками стиля и типов.
Стек: uv, Ruff, mypy, pre-commit.

## Установка и запуск

### Требования

- Linux или macOS (на Windows через WSL);
- `git`, `make`, `curl`.

Python и `uv` ставить заранее не нужно: `make setup` сам установит `uv` (если его нет),
а `uv` скачает нужную версию Python (3.12, зафиксирована в `.python-version`).

### Поднять окружение с нуля

```bash
git clone https://github.com/Lutichek/PAD_HW.git
cd PAD_HW
make setup
```

`make setup` создаёт `.venv`, ставит зависимости строго по `uv.lock` (включая группу `dev`)
и устанавливает git-хуки pre-commit.

### Команды

| Команда             | Что делает                                                        |
|---------------------|-------------------------------------------------------------------|
| `make setup`        | Поднимает окружение с нуля и ставит pre-commit хуки               |
| `make check`        | Все проверки: Ruff (линтер + формат) и mypy (strict). Ничего не меняет, при ошибках возвращает ненулевой код |
| `make lint`         | Только линтер Ruff                                                |
| `make format-check` | Только проверка форматирования                                    |
| `make typecheck`    | Только mypy                                                       |
| `make pre-commit`   | Прогнать pre-commit хуки по всем файлам                           |
| `make format`       | Автоисправление стиля и форматирование (меняет файлы)             |
| `make clean`        | Удаляет `.venv` и кеши инструментов                               |
| `make help`         | Список команд                                                     |

Запуск отладочного скрипта:

```bash
uv run python -m pad_hw.debug
```

### Проверки при коммите

Хуки pre-commit (`.pre-commit-config.yaml`) на каждом коммите запускают Ruff и mypy;
коммит с ошибками стиля или типов блокируется. Версии инструментов в хуках совпадают
с версиями в группе `dev` в `pyproject.toml`.

### Работа с репозиторием

Ветка `main` защищена: прямой push запрещён, изменения принимаются только через pull request
с успешно пройденным CI (`.github/workflows/ci.yml` выполняет `make setup && make check`).

## Данные

Сырые данные (архив CIFAR-10) лежат в S3 в неизменном виде, а обработанный датасет
собирается из них одной командой и выкладывается обратно в S3 с версией.

Дополнительно к требованиям из раздела выше нужен Docker с плагином `docker compose`.

### Хранилище S3

Локальное S3-совместимое хранилище [RustFS](https://github.com/rustfs/rustfs)
поднимается через `docker-compose.yml`:

- `s3`: RustFS `1.0.4`, данные лежат в именованном volume `s3-data` и переживают
  `docker compose down`; у сервиса есть healthcheck;
- `s3-init`: одноразовый контейнер с AWS CLI, ждёт готовности `s3` и создаёт бакет, если его нет.

Логин, пароль, имя бакета и порты берутся из `.env`. Пример лежит в `.env.example`;
`make s3-up` сам копирует его в `.env`, если файла ещё нет. Реальный `.env` не коммитится.

Где посмотреть содержимое:

- веб-консоль RustFS: <http://localhost:9001/rustfs/console/>, логин и пароль
  `S3_ACCESS_KEY` / `S3_SECRET_KEY` из `.env`;
- из терминала: `make s3-ls` (корень бакета) или, например, `make s3-ls S3_PATH=processed/cifar10/v1/`;
- любой S3-клиент (AWS CLI, `rclone`, Cyberduck) с адресом `http://localhost:9000`.

### Порядок команд

```bash
make setup     # окружение (один раз)
make s3-up     # поднять хранилище и создать бакет
make ingest    # скачать архив с сайта CIFAR и положить в S3: raw/cifar-10-python.tar.gz
make data      # собрать датасет и выложить в S3: processed/cifar10/v1/
make s3-down   # остановить хранилище (данные сохраняются)
```

- `make ingest` идемпотентен: если архив уже есть в S3, он ничего не скачивает и не загружает.
  Существующий объект в `raw/` никогда не перезаписывается. Скачивание с сайта университета
  бывает медленным (у нас около 150 КБ/с, то есть 15-20 минут на 163 МБ).
- `make data` с той же версией второй раз завершится ошибкой `Version v1 already exists`:
  версии неизменяемы. Чтобы собрать датасет с другими параметрами, укажите новую версию:

  ```bash
  make data VERSION=v2 SEED=7
  make data VERSION=v3 VAL_SIZE=10000 SEED=123
  ```

- `make s3-purge` останавливает хранилище и удаляет volume со всеми данными.

`make data` запускает шаги по очереди; каждый шаг можно запустить и отдельно
(`make data-split SEED=7`) или напрямую через его CLI (`uv run python -m pad_hw.data.split --help`):

| Шаг | Цель Makefile | Модуль | Что делает |
|-----|---------------|--------|------------|
| 0 | `data-check-version` | `pad_hw.data.publish --check-only` | Проверяет, что версии `VERSION` ещё нет в S3 (чтобы не обрабатывать данные зря) |
| 1 | `data-download` | `pad_hw.data.download` | Скачивает `raw/cifar-10-python.tar.gz` из S3 в `data/raw/` и сверяет MD5 |
| 2 | `data-convert` | `pad_hw.data.convert` | pickle -> PNG в `data/processed/cifar10/images/` и полная разметка train/test в `data/interim/cifar10/annotations/` |
| 3 | `data-split` | `pad_hw.data.split` | Стратифицированное разбиение train на train/val, пишет `data/processed/cifar10/annotations/{train,val,test}.json` |
| 4 | `data-stats` | `pad_hw.data.stats` | Среднее и std по каналам R, G, B только по train, пишет `stats.json` |
| 5 | `data-publish` | `pad_hw.data.publish` | Пишет `manifest.json` и выгружает всё в `processed/cifar10/<VERSION>/` |

Код разложен по модулям: `pad_hw.settings` (настройки из окружения), `pad_hw.s3` (работа с S3),
`pad_hw.data.*` (шаги конвейера). Локальная папка `data/` в git не попадает.

**Про pickle.** Python-версия CIFAR хранится в pickle, а загрузка pickle может выполнить
произвольный код. Поэтому архив распаковывается только после сверки MD5 с официальным
значением, а сам pickle читается ограниченным распаковщиком: разрешены только классы numpy,
нужные для восстановления массивов.

### Что лежит в S3

```
s3://pad-hw/
├── raw/
│   └── cifar-10-python.tar.gz       # архив с сайта, как есть
└── processed/
    └── cifar10/
        └── v1/
            ├── images/              # 60 000 PNG: train_00000.png ... test_09999.png
            ├── annotations/
            │   ├── train.json       # 45 000 картинок
            │   ├── val.json         # 5 000 картинок
            │   └── test.json        # 10 000 картинок
            ├── stats.json           # mean и std по каналам (по train)
            └── manifest.json
```

Формат разметки (один файл на выборку):

```json
{
  "classes": ["airplane", "automobile", "bird", "..."],
  "images": [
    {
      "image_id": "train_00000",
      "file_name": "images/train_00000.png",
      "label": 6,
      "label_name": "frog",
      "sha256": "..."
    }
  ]
}
```

`sha256` считается по байтам PNG-файла. Картинки при разбиении не переименовываются:
картинка из валидации сохраняет `image_id` вида `train_...`.

`manifest.json` содержит число картинок в каждой выборке, список файлов разметки и статистик
с размерами и `sha256`, параметры обработки (`val_size`, `seed`), хеши исходного архива
и git-коммит, на котором выполнялась обработка. Он загружается последним, поэтому его
наличие означает, что версия выгружена целиком.

### Карточка датасета

| | |
|---|---|
| **Название** | CIFAR-10 |
| **Источник** | <https://www.cs.toronto.edu/~kriz/cifar.html>, версия для Python (`cifar-10-python.tar.gz`, 163 МБ, MD5 `c58f30108f718f92721af3b95e74349a`) |
| **Авторы** | Alex Krizhevsky, Vinod Nair, Geoffrey Hinton. Learning Multiple Layers of Features from Tiny Images, 2009 |
| **Состав** | 60 000 цветных изображений 32x32 (RGB), 10 классов по 6 000 картинок |
| **Классы** | airplane, automobile, bird, cat, deer, dog, frog, horse, ship, truck |
| **Исходное разбиение** | train 50 000 (по 5 000 на класс), test 10 000 (по 1 000 на класс) |
| **Наше разбиение (v1)** | train 45 000 / val 5 000 / test 10 000; val выделен из исходного train стратифицированно (по 500 картинок каждого класса), `seed=42`; test не менялся |
| **Нормализация (train v1)** | mean = (0.491840, 0.482541, 0.446820), std = (0.247051, 0.243542, 0.261692) по каналам R, G, B (значения пикселей / 255) |

Известные проблемы:

- **Низкое разрешение.** 32x32 пикселя: мелкие детали теряются, некоторые картинки
  трудно классифицировать даже человеку.
- **Ошибки разметки.** В тесте есть картинки с неверной меткой (по оценке Northcutt et al., 2021,
  около 0.5% тестовой выборки).
- **Почти дубликаты между train и test.** Около 3% тестовых картинок имеют почти точные копии
  в train (Barz, Denzler, 2020: "Do we train on test data?"), это немного завышает метрики на тесте.
- **Пересекающиеся классы.** `automobile` и `truck` не пересекаются по определению авторов
  (пикапы не входят ни в один класс), но визуально классы близки; то же для `cat` и `dog`.
- **Сдвиг распределения.** На новой выборке из того же источника (CIFAR-10.1, Recht et al., 2018)
  точность моделей падает на несколько процентов: тестовая выборка не идеально
  представляет «реальные» картинки.
- **Формат pickle небезопасен** (см. выше), поэтому мы конвертируем данные в PNG и JSON.
